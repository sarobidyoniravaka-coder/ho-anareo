💣 Simulation d'attaque par bombe logique

Démonstration pédagogique du fonctionnement d'une bombe logique et des mesures permettant de s'en protéger.

1. Qu'est-ce qu'une bombe logique ?

Une bombe logique est un fragment de code malveillant inséré dans un programme ou un système légitime. Contrairement à un virus, elle ne se propage pas : elle reste dormante et invisible jusqu'à ce qu'une condition de déclenchement précise soit remplie. Une fois déclenchée, elle exécute sa charge utile (payload), souvent destructrice.

Déclencheurs courants

  • 🕒 Temporel : une date ou une heure précise (« bombe à retardement »).
  • 👤 Événementiel : la suppression d'un compte, le départ d'un employé, une modification dans une base de données.
  • 📡 Absence de signal : un « interrupteur de l'homme mort » (dead man's switch) qui s'active si une personne ne se connecte plus pour « réarmer » le système.

Pourquoi c'est dangereux ?

Le code reste invisible parmi des milliers de lignes légitimes. Il est souvent introduit par une personne ayant un accès interne (menace interne) ou via une dépendance / mise à jour compromise (attaque de la chaîne d'approvisionnement). Les dégâts peuvent être très étendus : suppression de fichiers, corruption de bases de données, désactivation de comptes administrateurs, etc.

📚 Cas réel connu : en 1996, un administrateur système licencié d'une entreprise américaine (Omega Engineering) avait laissé un programme malveillant programmé pour s'activer quelques semaines après son départ, supprimant la quasi-totalité des fichiers de conception de l'entreprise. Ce cas est souvent cité comme l'un des premiers procès liés à une bombe logique.

    3. Solutions et bonnes pratiques

    Aucune mesure n'est infaillible seule : c'est leur combinaison (défense en profondeur) qui permet de prévenir, détecter et limiter l'impact d'une bombe logique.

    🔍 Revue de code & analyse statique (SAST)

    Faire relire chaque modification par un autre développeur (« four eyes ») et utiliser des outils d'analyse statique pour repérer du code suspect avant la mise en production.

    🔐 Principe du moindre privilège

    Limiter les droits de chaque compte (humain ou de service) au strict nécessaire, afin que même un code malveillant ne puisse pas tout détruire.

    👀 Surveillance & détection (EDR / SIEM)

    Mettre en place des alertes sur les comportements anormaux : suppression massive de fichiers, modification de scripts planifiés, créations de tâches cron inhabituelles.

    🚪 Gestion du départ des employés

    Désactiver immédiatement tous les accès lors d'un départ ou d'un licenciement, et auditer le code écrit récemment par la personne concernée.

    💾 Sauvegardes régulières et testées

    Appliquer la règle 3-2-1 (3 copies, 2 supports différents, 1 hors site) et tester régulièrement la restauration pour garantir qu'elle fonctionne.

    🧾 Traçabilité & gestion de version

    Utiliser un système de contrôle de version avec historique complet et commits signés, pour savoir qui a écrit quoi et pouvoir auditer le code facilement.

    🧪 Audits et tests de sécurité réguliers

    Réaliser des audits de code et des tests d'intrusion périodiques pour détecter du code dormant ou des portes dérobées avant qu'elles ne soient exploitées.

    ✅ Validation obligatoire avant déploiement

    Exiger une approbation (« pull request » validée) et des tests automatisés avant que tout changement n'atteigne la production.
